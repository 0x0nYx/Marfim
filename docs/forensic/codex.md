## 1. Identity & Purpose (what it is, who maintains it, current version)

- Codex CLI is OpenAI's local coding agent: an interactive terminal UI (`codex-rs/tui/`), a non-interactive runner (`codex-rs/exec/`), and a headless app-server consumed by IDE extensions and SDKs. `README.md` self-describes: "Codex CLI is a coding agent from OpenAI that runs locally on your computer," and distinguishes the IDE extension and the Codex desktop app (`codex app`) from the cloud product ("Codex Web").
- Maintained by OpenAI with external contributors (`CHANGELOG.md` credits community PRs such as #44557; `docs/CLA.md` governs contributions). Documentation lives at `developers.openai.com/codex` per `docs/config.md` / `docs/skills.md`.
- Version: Rust workspace declares `version = "0.0.0"` (`codex-rs/Cargo.toml:173`) and npm `@openai/codex` is `0.0.0-dev` (`codex-cli/package.json`). Release versions and the build commit are stamped at packaging time — `codex-rs/build-info/src/lib.rs` resolves the packaged version plus `STABLE_GIT_COMMIT` (via `codex-rs/install-context`). The current release number is therefore not recoverable from the repo (unclear; `CHANGELOG.md` defers to GitHub releases).
- Distribution channels: standalone install scripts (chatgpt.com/codex/install.sh), `releases.openai.com/codex` with GitHub Releases fallback (`CODEX_INSTALLER_USE_RELEASES_OPENAI_COM`), npm wrapper, Homebrew cask (`README.md`).
- Auth modes: "Sign in with ChatGPT" (OAuth, recommended for plan users) or an OpenAI API key requiring extra setup (`README.md`; implementation `codex-rs/login/`).

## 3. Agent Loop (turn lifecycle, streaming, tool dispatch, retries, compaction)

- Submission: clients send `Op` variants (`protocol/src/protocol.rs:705` — `Interrupt`, `InterruptIfNoPendingInput`, `CleanBackgroundTerminals`, realtime conversation ops, user-input turns) via `CodexThread::submit` (`core/src/codex_thread.rs:244`) / `submit_with_trace` (:451); events come back through `CodexThread::next_event` (:873). `ThreadManager` (`core/src/thread_manager.rs:264`) creates, resumes, and forks threads.
- Turn body: `run_turn` at `core/src/session/turn.rs:178`. Sequence (paths under `core/src/`):
  1. Input guards: reject uploaded-audio input, drain late hook results from the previous turn, run pending Guardian checkpoint for review sessions (`turn.rs:196-206`; `guardian/`).
  2. Pre-sampling compaction: `run_pre_sampling_compact` (`turn.rs:1457`) compacts *before* the new user message is recorded if the budget would overflow; failures emit `EventMsg::Error` and abort the turn.
  3. Environment/MCP prep: resolve required MCP servers/plugins mentioned by the input (`required_mcp_servers_for_input`, `turn.rs:1075`), capture `StepContext` (seeds tools, skills, plugins for this step).
  4. Context recording: record context updates + turn diff display roots concurrently (`turn.rs:320`, `turn_diff_tracker.rs`).
  5. Prompt assembly: per-step `build_prompt` (`turn.rs:1751`) producing `Prompt` (`core/src/client_common.rs`): input items, tool specs, parallel_tool_calls flag, base instructions, output schema. Context sources merged upstream: cloned history (`context_manager/history.rs`), AGENTS.md project docs (`agents_md.rs`), environment context, skills catalog (`skills.rs`), developer blocks `<permissions>` / `<apps_instructions>` / `<collaboration_mode>` / `<skills_instructions>` (config flags, `config/mod.rs:750-772`), world-state diffs (`session/world_state.rs`).
  6. Sampling: `run_sampling_request` (`turn.rs:1792`) → `ModelClient::stream` (`client.rs:2510`). Transport is Responses API over WebSocket when enabled, else HTTP SSE; a WS failure permanently downgrades the session to HTTP (`try_switch_fallback_transport`, `client.rs:2559`).
  7. Streaming: `ResponseEvent`s are consumed in the turn loop; assistant text is parsed incrementally (`AssistantMessageStreamParsers`, `turn.rs:2127`) emitting `AgentMessageDelta` events; plan-mode segments produce `PlanUpdate` (`handle_plan_segments`, `turn.rs:2404`).
  8. Tool dispatch: function calls route through the tool registry/router (`tools/registry.rs`, `tools/router.rs`), orchestrated (parallel calls allowed per `Prompt.parallel_tool_calls`; `tools/orchestrator.rs`, `tools/parallel.rs`), wrapped by `PreToolUse`/`PostToolUse` hooks (`hook_runtime.rs`), per-call dispatch traces (`tools/tool_dispatch_trace.rs`), and approval escalation (`tools/approvals.rs`, `tools/network_approval.rs`).
  9. Post-sampling: token status computed (`session/context_window.rs`); async compaction may start mid-turn or post-turn (`session/async_compaction.rs`); queued user input can be folded into a follow-up step (steering) instead of starting a new turn (`session/input_queue.rs`; `needs_follow_up` logic `turn.rs:632-660`).
- Retries: shared exponential backoff `backoff(attempt)` — 200 ms initial, ×2 per attempt, ±10% jitter (`codex-rs/async-utils/src/backoff.rs`). Per-provider knobs `request_max_retries`, `stream_max_retries`, `stream_idle_timeout_ms` on `ModelProviderInfo` (`model-provider-info/src/lib.rs:209-214`) with hard caps noted at lib.rs:78-80. Stream error handling in `core/src/responses_retry.rs`: connection retries start at 5 s and cap at 60 s (constants at top of file); server `Retry-After` advice is honored without extending the retry budget; exhausted advice is retained (`ExhaustedResponseRetry`) for a later reattempt; auth-refresh produces `PendingUnauthorizedRetry` (`client.rs:2860-2901`).
- Event model: `EventMsg` (`protocol/src/protocol.rs:1535`) is the single event stream per thread — streaming deltas (`AgentMessageDelta`-family), lifecycle (`TurnStarted/TurnCompleted`-style items), command telemetry (`ExecCommandBegin/End` protocol.rs:1650/1658), MCP (`McpToolCallBegin/End` 1637/1639), web search (`WebSearchBegin` 1641), plan (`PlanUpdate` 1714), diffs (`TurnDiff` 1709), token accounting (`TokenCount` 1599), and approval requests (`ExecApprovalRequest` 1663, `ApplyPatchApprovalRequest` 1686). Item-based persistence uses `TurnItem` / `codex_protocol::items` (e.g. `ContextCompactionItem`); the app-server projects these into v2 notifications (`v2/ItemStartedNotification.ts`, `v2/ItemCompletedNotification.ts`).
- Steering & interruption: queued user input during an active turn is either folded into the running turn (`session/input_queue.rs` mailbox delivery, turn.rs:632) or starts a new turn; `Op::InterruptIfNoPendingInput` allows clients to cancel only idle turns (protocol.rs:710); v2 exposes `TurnSteerParams` / `TurnInterruptResponse` schema types. Background terminals survive interrupts until `Op::CleanBackgroundTerminals` (protocol.rs:718).
- Compaction: `core/src/compact.rs` builds replacement history using `SUMMARIZATION_PROMPT` from `codex-rs/prompts/src/compact.rs`; it preserves the initial context and recent real user/agent messages (`insert_initial_context_before_last_real_user_or_summary`, `compact.rs:651`), caps the summarization user message at 20k tokens (`COMPACT_USER_MESSAGE_MAX_TOKENS`, compact.rs:78), and persists compaction checkpoints (`codex-rs/history/src/compaction_checkpoint.rs`). Thresholds: `model_auto_compact_token_limit` (+ scope), `model_post_turn_compact_threshold_percent`, `async_compaction_threshold_percent` (`config/mod.rs:658-670`). Remote v2 compaction delegates summarization to the backend, with image budgets and fallback models (`core/src/compact_remote_v2.rs`, `compact_model_fallback.rs`).

## 5. Model/Provider Layer

- `ModelProviderInfo` (`codex-rs/model-provider-info/src/lib.rs`): `base_url` (default `https://api.openai.com/v1`, lib.rs:482), `env_key`, `requires_openai_auth`, custom headers/query params, `request_max_retries`, `stream_max_retries`, `stream_idle_timeout_ms` (lib.rs:209-214). **`wire_api` supports only `responses`**: `WireApi` has a single variant (lib.rs:116-120) and the Chat Completions wire API was removed with an actionable error (lib.rs:109); `ollama-chat` provider removed likewise (lib.rs:111).
- Built-in provider id `openai` (`OPENAI_PROVIDER_ID`, lib.rs:85). Local/OSS providers via dedicated crates `codex-rs/ollama` and `codex-rs/lmstudio`. AWS Bedrock GPT deployment IDs + SigV4 supported (`AMAZON_BEDROCK_*` constants lib.rs:93-106; `codex-rs/aws-auth`); GCP settings types exist in protocol (`app-server-protocol/schema/typescript/v2/GcpSettingsParams.ts`).
- Custom providers: `config.toml` `[model_providers.<id>]` with `base_url`, `env_key`, etc.; selected by `model_provider` key into that map (`Config.model_provider_id` / `Config.model_provider`, `core/src/config/mod.rs:672-676`; defaults `codex-rs/config/src/model_provider_defaults.rs`).
- Model catalog: `codex-rs/models-manager` ships bundled `models.json` (12 models at this commit; GPT-5.6/6.x family, e.g. `gpt-6.1-terra` context_window 500000, others 272000) and refreshes from OpenAI discovery or a provider-specific catalog URL ("Optional full URL for a Codex-native model catalog", lib.rs:154). Per-model `ModelInfo` drives behavior: `shell_type`, `apply_patch_tool_type`, `experimental_supported_tools`, `use_responses_lite`, truncation/context budgets (`models-manager/src/model_info.rs`; consumed by `core/src/tools/spec_plan.rs`). Collaboration-mode presets and originator metadata also live here (`collaboration_mode_presets.rs`, `originator.rs`).
- Transports: Responses API SSE (HTTP) or WebSocket with fallback and sticky turn-state routing headers `x-codex-beta-features` / `x-codex-turn-state` (`core/src/client.rs:2510-2630`); WebSocket auth handled in `codex-rs/websocket-auth`/`websocket-client`. `codex-rs/responses-api-proxy` is an internal proxy that fronts the Responses API (e.g. for Bedrock OIDC auth — `responses-api-proxy/src/github_oidc.rs`).

## 6. Permissions & Safety

- Approval policy `AskForApproval` (`protocol/src/protocol.rs:1163-1186`): `untrusted` (UnlessTrusted — commands need approval unless an execpolicy rule allows them), `on-request` (default; serde alias `on-failure`), `granular` (`GranularApprovalConfig` — per-category booleans; `false` auto-rejects instead of prompting), `never` (failures returned to the model, never escalated).
- Sandbox selection: config-level `SandboxMode` (`protocol/src/config_types.rs:104-114`): `read-only` (serde default), `workspace-write`, `danger-full-access`. Runtime `SandboxPolicy` (`protocol/src/protocol.rs:1249+`): `DangerFullAccess`, `ReadOnly{network_access}`, `ExternalSandbox{network_access}` (assumes an outer sandbox exists), `WorkspaceWrite{writable_roots, network_access, ...}` (`get_writable_roots_with_cwd` protocol.rs:1424).
- Permission profiles (newer model): named profiles under `[permissions]` with `default_permissions = "workspace"` style selection; profiles compile filesystem+network rules into `PermissionProfile` (`core/src/config/permissions.rs`, `permission_profile_catalog.rs`, `permission_profile_selection.rs`, `resolved_permission_profile.rs`; network example in `network-proxy/README.md`). Legacy `sandbox_mode` remains supported (`linux-sandbox/README.md` "Legacy `SandboxPolicy` / `sandbox_mode` configs remain supported").
- Execpolicy: Starlark-dialect rules — `prefix_rule(pattern=[...], decision=allow|prompt|forbidden, justification, match/not_match self-tests)` and `host_executable(name, paths)` constraining basename fallback (`codex-rs/execpolicy/README.md`). Rule files loaded from `$CODEX_HOME/rules/*.rules` (`core/src/exec_policy.rs:56-58`); `--ignore-rules` skips them (`exec/src/cli.rs`). Users can amend policy through approval (`ReviewDecision::ApprovedExecpolicyAmendment`).
- macOS: Seatbelt via `/usr/bin/sandbox-exec` only (path pinned to resist tampering, `sandboxing/src/seatbelt.rs:57-61`) with embedded SBPL: base, network, preferences, and read-only platform-default policies (`seatbelt.rs:20-27` + `seatbelt_*.sbpl`); a Seatbelt daemon variant exists (`seatbelt_daemon.rs`).
- Linux: bubblewrap is the default filesystem sandbox — prefers `bwrap` found on PATH outside cwd, handles old-bwrap `--argv0` compat, falls back to a bundled `codex-resources/bwrap` binary, warns at startup when missing; seccomp via `seccompiler` with `PR_SET_NO_NEW_PRIVS` (`linux-sandbox/README.md`; `linux-sandbox/src/seccomp.rs`); legacy Landlock implementation retained (`sandboxing/src/landlock.rs`); optional PID namespace (`sandboxing/src/linux_pid_namespace.rs`); WSL1 rejected, WSL2 fine (`linux-sandbox/README.md`).
- Windows: `windows-sandbox-rs` (+ broker `windows-sandbox-service`), `mxc-sandbox` built on Microsoft's `mxc` SDK (workspace git dep, `codex-rs/Cargo.toml:436`), setup/readiness flows surfaced in protocol (`v2/WindowsSandbox*` schema files) and `core/src/windows_sandbox*.rs`.
- Network: `codex-network-proxy` runs loopback HTTP proxy (default 127.0.0.1:3128) and SOCKS5 (127.0.0.1:8081; Windows port ranges documented) enforcing allow/deny and a "limited" read-only mode (`network-proxy/README.md`); Linux bwrap integrates via managed proxy routing (`linux-sandbox/src/proxy_routing.rs`, `managed_proxy.rs`); Seatbelt has a dedicated network policy SBPL. Per-host allow/deny rules can be persisted from approvals (`ReviewDecision::NetworkPolicyAmendment`, protocol.rs:4477-4481) and computed at runtime (`core/src/network_policy_decision.rs`).
- Approval decisions `ReviewDecision` (`protocol/src/protocol.rs:4454-4486`): `Approved`, `ApprovedExecpolicyAmendment`, `ApprovedForSession`, `ApprovedMcpPolicyAmendment`, `NetworkPolicyAmendment`, `Denied{rejection}`, `TimedOut`, `Abort` (default is a denial).
- Escalation pipeline: sandbox-denied commands are classified (`sandboxing/src/violation.rs`, `denial.rs`) and re-run with escalation through `exec_policy.rs` + `tools/approvals.rs`; approval routing to a human or to the automated Guardian reviewer is configured via `approvals_reviewer` (`config/mod.rs:691-694`).
- Escalation sequence for a blocked command: (1) the tool handler runs the command under the effective sandbox; (2) a sandbox denial is detected and classified (`sandboxing/src/denial.rs` distinguishes executor-managed vs Codex sandbox denials); (3) policy (`exec_policy.rs`) decides whether escalation is permitted under the active `AskForApproval`; (4) an approval request event is emitted and routed (human UI or Guardian reviewer per `approvals_reviewer`); (5) the decision may re-run the command with elevated permissions or amend stored rules. `codex execpolicy` subcommand exists for standalone rule evaluation (`cli/src/main.rs:259-261`); `codex sandbox` runs arbitrary commands under the harness sandbox.
- Guardian (automated safety review): review sessions with circuit breaker, transcript format control, and policy templates rendered into a fixed prompt (`core/src/guardian/`, `core/src/guardian_review.rs`, config fields `guardian_*` at `config/mod.rs:719-748`; reviewer extensions `ext/guardian-*`). `hook_runtime.rs` also enforces `PermissionRequest` hooks before prompting.

## 11. Standout Features

1. **Unified PTY exec tool** — one `exec_command` tool covers one-shot and resumable interactive sessions via `write_stdin`, replacing separate shell tools (`core/src/tools/handlers/shell_spec.rs`, `handlers/unified_exec/`).

3. **Starlark execpolicy** — prefix rules with allow/prompt/forbidden decisions, self-testing `match/not_match` examples, and host-executable path pinning (`codex-rs/execpolicy/README.md`).
4. **Four-platform sandboxing behind one manager** — Seatbelt SBPL (macOS), bwrap+seccomp with Landlock legacy (Linux), brokered sandbox + Microsoft mxc (Windows) (`codex-rs/sandboxing/src/manager.rs`, `seatbelt.rs`, `landlock.rs`, `windows_mxc.rs`).
5. **Local network enforcement proxy** — loopback HTTP+SOCKS5 proxy with allow/deny/"limited" modes and persistable per-host amendments from approvals (`network-proxy/README.md`).
6. **Async + remote compaction** — background compaction mid-turn without blocking, plus backend-delegated summarization with image budgets (`core/src/session/async_compaction.rs`, `core/src/compact_remote_v2.rs`).
7. **Tool search deferral** — BM25 `tool_search` over deferred namespaces keeps prompt tool lists small (`codex-rs/tools/src/tool_search.rs`).
8. **Code Mode** — V8-powered JavaScript orchestration of tool calls with a standalone host process, gRPC transport, prewarm, and output truncation (`features/src/lib.rs:148-166`; crates `code-mode*`, `v8-poc`).
9. **Multi-agent orchestration** — spawn/role-based sub-agents with identity, roles, and an MCP-exposed message board for inter-agent messaging (`core/src/agent/`, `codex-rs/message-board/`).
10. **App-server daemon** — shared background server that TUI/IDE/SDK clients attach to, with managed install/update lifecycle and remote control (`app-server-daemon/src/update_loop.rs`, `launch.rs`).
11. **Dual persistence** — date-sharded JSONL rollouts (transparent compression, ordinal per line) plus a migrated-able SQLite state DB (`codex-rs/rollout/src/`, `codex-rs/state/src/migrations.rs`).
12. **Responses over WebSocket with HTTP fallback** — sticky turn routing, beta headers, permanent downgrade after retry exhaustion (`core/src/client.rs:2510-2570`).
13. **Guardian automated reviewer** — separate review sessions with circuit breaker, transcript encoding control, and templated policy prompts (`core/src/guardian/`, `codex-rs/prompts/src/guardian_instructions.rs`).
14. **Model catalog manager** — bundled + remotely refreshed model metadata driving tool gating, effort presets, and collaboration modes (`codex-rs/models-manager/models.json`, `src/model_info.rs`).
15. **Rich hook system** — lifecycle events including `PreModelRequest`/`PermissionRequest`, trust levels, and managed-only enforcement (`hooks/src/lib.rs:105-120`).
16. **Realtime voice** — WebRTC realtime conversations integrated with the same turn engine (`core/src/realtime_conversation.rs`, `codex-rs/realtime-webrtc/`).

## 12. Lessons for Marfim

- **Adopt: per-turn tool spec planning.** Make tool availability a pure function of (config, model info, feature flags, environments) computed each turn — it is testable, auditable, and keeps model-specific quirks out of handlers (`core/src/tools/spec_plan.rs`).
- **Adopt: protocol-first, generated bindings.** One `protocol` crate with `Op`/`EventMsg` and ts-rs-generated TS types lets TUI, exec, IDE, and SDKs share a single contract without drift (`codex-rs/protocol`, `app-server-protocol/schema/typescript`).
- **Adopt: JSONL rollouts + separate SQLite state.** Human-readable, date-sharded, ordinal-numbered sessions for resume/debug, with structured state in a migrated DB — plus explicit migration commands when formats change (`codex-rs/rollout/src/`, `state/src/migrations.rs`).
- **Adopt: sandbox as a manager trait, not a flag.** Pluggable Seatbelt/bwrap/seccomp/Windows backends behind one `SandboxManager`, with violation classification feeding approval/escalation flows (`sandboxing/src/manager.rs`, `violation.rs`).
- **Adopt: amendment-capable approvals.** Treating approvals as potential policy edits (execpolicy/network/MCP/session-cache amendments) converts repetitive prompts into durable, reviewable rules (`protocol/src/protocol.rs:4454-4486`).
- **Adopt: compaction as a pipeline, not a command.** Pre-sampling checks, inline fallback, async background runs, and persisted checkpoints keep long sessions alive without user intervention (`core/src/compact.rs`, `session/async_compaction.rs`).
- **Adopt: AGENTS.md-style layered project docs** with root-marker discovery, override files, and a byte budget — cheap, standards-friendly memory (`core/src/agents_md.rs`).
- **Avoid: crate explosion.** 166 workspace crates for one CLI yields a heavy build graph and constant naming churn (many "Removed compatibility flag" entries in `features/src/lib.rs`); consolidate utilities.
- **Avoid: removing wire APIs without bridges.** Codex deleted Chat-Completions support outright (`model-provider-info/src/lib.rs:109-111`); Marfim should isolate the wire format behind a small trait from day one so provider variance is a config matter, not a breaking change.
- **Avoid: unbounded config surface.** Hundreds of flat keys + profiles + managed layers + feature flags is hard to document and test; keep a small strict schema (`--strict-config`), provenance tracking, and push niche behavior into profiles (`core/src/config/mod.rs`, `codex-rs/config/src/constraint.rs`).
- **Scope note:** the concentration of engineering value is in the exec + sandbox + approval loop, the rollout/session layer, and the tool spec plan; realtime voice, desktop app, cloud tasks, and multi-agent boards are large surface areas a clean-room MVP can defer.
