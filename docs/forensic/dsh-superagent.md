## 1. Identity & Purpose

- Self-description: "a proactive coding agent for one GitHub repository, packaged as a bundle for DeepSeek Harness (DSH)". It listens to GitHub and optionally Feishu; when an allowed person asks for work it opens a work item, executes it in its own agent session and directory, and answers in the original conversation (e.g., with a pull request). A web panel shows what needs a person (README.md lines 7; package.json `description`).
- Governing principle: "take as little human attention as possible, and give as much value as possible" — the agent acts only when asked or when a written rule allows it, and speaks only when a person must act or can use a result (README.md line 9; docs/000-philosophy.md).
- Explicitly labeled a research prototype, not an official product; README warns it is adapted from an internal version and from the paper "Exploring Super-agent Design: Towards a More Autonomous Agent System", and that some paper designs are not implemented (README.md lines 3–5).
- The repo's own vocabulary maps to the task context as: work item = **Ticket**; main router session = **main Session / orchestrator**; source plugins = **Sources** (docs/001-domain.md glossary, lines 77–112).
- Deployment shape: one dedicated DSH profile (`superagent`, created from the Web profile template) running the bundle, a panel served on `127.0.0.1` (default port 3082), one agent GitHub account (a real user account, not a GitHub App, because the Source reads the account's notifications), and an optional Feishu bot (docs/006-deployment.md "What runs", "Agent GitHub account"; examples/profile.cordis.patch.yml).
- Forensic naming history: the environment writer still owns and replaces marker files of earlier project names `dsh-tag`, `dsh-go`, `dsh-freelancer` (src/infra/environment.ts `LEGACY_MARKERS`), indicating this prototype was renamed at least three times internally before publication.

## 3. Agent Loop (how the router session and worker sessions run; tool dispatch; approvals; cite files)

- **Router loop.** The main Session is a persistent DSH agent created by `Sessions.ensure` with the router preset and `danger-full-access` permissions (src/app/sessions.ts). It never polls: candidate cards, follow-up notices, worker reports and completed job results are steered into its turn as messages. The `relay` and `notice` effect kinds deliver them in order (`Sessions` constructor registers the handlers; src/app/sessions.ts; src/app/effects.ts table). A `noWait` tool guard refuses `sleep`, shell `timeoutMs` > 30 s and `job_output` waits > 5 s so a blocked step cannot delay incoming candidates (src/app/sessions.ts `noWait`; prompts/orchestrator.md).
- **Trigger → decision.** Every 2 seconds (and on demand) a Pass runs due effects then `Engine.evaluateDue`, which starts one Eval per Thread with queued Triggers batched together, requeues expired Evals (twice) and records `unavailable` on the third expiry (src/app/passes.ts; src/core/engine.ts `evaluateDue`). The gate in `settingsPolicy().gate` (src/policy.ts) decides admissibility and strength deterministically; admitted inferred candidates are delivered to the main Session through the `assessment` effect (MasterAssessor, src/app/assessment.ts).
- **Assessment protocol.** The router assesses proactive candidates in-Session with three read-only tools: `orchestrator_eval` (loads a bounded thread window: 5 first messages + 5 around the trigger, images included), `orchestrator_eval_read` (message/root/parent/thread page/file/directory/image), and `orchestrator_eval_decide` (structured schema: decision, one `rule_assessments` entry per enabled rule, `direction` {implementation_requested, target_basis, requires_design_decision, evidence}, title, scope, worktree_name, intent_evidence, acknowledgement) (src/app/tools/main.ts; src/app/assessment.ts `AssessmentSchema`; prompts/admission.md).
- **Accept conversion.** `assessmentOutcome` (src/policy.ts) hard-validates: exactly one judgement per enabled rule, settled direction, ≥1 matched rule, `intent_evidence` present; an inferred accept outside `auto` mode is downgraded to an `ignore` recorded as "would accept" (observe mode). `Engine.decide` then creates Ticket + Mandate + Assignment + Subscriptions + acknowledgement atomically (src/core/engine.ts; src/core/evals.ts).
- **Batch routing.** `orchestrator_route` takes 1–20 accept/attach/stop/ignore items; each item runs as its own Engine transaction, is validated per-kind field-by-field (`FIELDS`), and a refused item does not stop the others (src/app/tools/main.ts `routeTool`; docs/007-architecture.md "Main Session tools").
- **Worker loop.** Launch is a durable `launch` effect: reserve a WorkerSlot → run the prepare command (`sh -c`, 10 min timeout, env vars) → create/reuse session `worker-<ticketId>` in the ticket directory → deliver the assignment message (title, ≤1500 chars assignment text, source trigger card) (src/executor/dsh.ts). Inputs (fan-out triggers, policy changes, resumes, notes, text) are delivered as ordered `delivery` effects; each Input is tracked until the Session takes it into history (`inputsRead`) and counts as read once a Report or turn end follows (src/core/engine.ts `inputsRead`; docs/007-architecture.md).
- **Worker self-management.** Workers report via `orchestrator_report` (progress/ready/blocked/failed/dropped + structured `human_action` question + optional `pr_number` which binds the PR under claim rules atomically with the report) (src/app/tools/executor.ts). Background shell jobs and subagents keep the worker slot alive after a turn; after 30 min jobs are killed and the worker is reported waiting; a handoff frees the slot immediately (src/executor/dsh.ts constants `BACKGROUND_LIMIT_MS` etc.; src/executor/background.ts).
- **Worker turn lifecycle.** `agent/status` idle triggers `turnEnded`; if shell jobs or subagents still run, a settling watcher keeps the slot and stays quiet until quiet or the 30-minute limit, then kills jobs and reports waiting with the worker's last words; a completed job wakes the worker with its result in the same slot. After a `ready` report or a question (or any blocked/failed report), handoff frees the slot immediately while left-behind jobs keep running without waking; when an Assignment ends its jobs are killed and subagents released, and the replacement Assignment starts only after that shutdown (src/executor/dsh.ts; src/executor/background.ts `runningJobs`/`untilQuiet`/`collectJobs`/`stopSubagents`; docs/003-execution.md "Background work and worker slots").
- **Approvals.** There is no per-command human approval: Executor Sessions run commands "without approval as the operator's OS user" (docs/003-execution.md). Control is front-loaded into authorization (gate/Mandate, §6) and delivery gates: auto-merge is a prompt-governed behavior (default: only the ticket's own PR, ready, approvals cover head commit, <200 changed lines, and never enabled as the agent account) (docs/003-execution.md "Merging"; prompts/team/delivery.md defaults). The structured approval surface is `human_action` questions surfaced as Attention on the panel.
- **Eval lifecycle timing.** An Eval's deadline starts only when its candidate card reaches the main Session (`candidateDelivered`), so queue/delivery time never consumes the budget; an undelivered candidate never expires; expiry requeues the batch twice, and the third consecutive expiry records `unavailable`; a Policy change under an Eval discards and requeues it (src/core/engine.ts `evaluateDue`; src/app/assessment.ts; docs/002-authorization.md "When Eval does not finish").
- **What the router actually receives.** Four steered message types: `candidate` (batch trigger cards, thread, related_tickets, tickets_total, delivered_to, referenced_tickets from links, handed_back reasons), `follow_up` (one message as its executor sees it, with the reminder that executors decide it), `worker_report` (ticket card, origin trigger, state and ≤600-char summary with read pointer when truncated), and `worker_attention` (ticket card carrying the question). Everything else — ticket_ended, settings_saved, prompt saves, requeues, unsubscribes — is injected as a background notice without waking the Session (docs/007-architecture.md "Messages delivered to Sessions"; src/app/notices.ts).
- **Decisions and reasons.** Decision kinds are accept/stop/ignore/unavailable; every Decision records `reason` as a list of typed `{code, values, triggerId}` entries from a closed `REASONS` set (e.g. `timeout`, `policyChanged`, `routed`, `startedTicket`, `not_a_member`, `said`), rendered for models via `reasonText` and localized in the panel by `reason.<code>` (src/core/reasons.ts; docs/007-architecture.md "Model"). Domain events emitted after each change: `trigger.received`, `eval.started`, `decision.recorded`, `ticket.created/resumed/ended`, `assignment.started/ended`, `thread.subscribed/unsubscribed`, `trigger.requeued`, `policy.changed` (docs/007-architecture.md; src/core/ports.ts `DomainEvents`).
- **Ticket stages gate the loop.** The stage table (person/delivery, person/answer, person/review, person/blocked, person/failed, working/queued, idle, working) is derived from stored facts (`waitsForPerson`, latest report, undelivered inputs) by `ticketStage` (src/core/stage.ts; src/core/model.ts `waitsForPerson`), and `canRetry` drives when `orchestrator_ticket_retry`/panel retry is offered (src/core/stage.ts).

## 5. Model/Provider Layer

- No model is pinned in the repo. Each role optionally configures `{provider, model, reasoningEffort}`: `eval.model` (assessment) and `executor.model` (worker); `null` means the DSH profile's default model (src/policy.ts `RoleModelSchema`, `EvalConfigSchema`, `ExecutorConfigSchema`; docs/006-deployment.md "a model provider configured for DeepSeek Harness").
- `resolveRoleModel` goes through `ctx.llm.resolveCallConfig` — "catalog membership is not a restriction", i.e. any provider the DSH LLM service resolves is allowed (src/app/role-models.ts). The role model is seeded only into a brand-new session by appending a `model/selection` session event (deliberately not `selectModel`, which would mutate the global DSH default); later manual selections win (src/app/role-models.ts `initializeRoleModel`).
- The worker preset's persona row renders "You are a coding agent powered by the {{model}} model" (cordis.patch.yml persona plugin); the router preset has no persona because its prompt is `complete: true` (src/app/sessions.ts system-prompt section).
- Model-budget failures are observable: `RetryHealth` tracks sessions waiting on a model-budget retry and reports them on the `models` health entry; passing provider/network failures are retried (3 attempts, backoff 15 s) and a worker whose turn failed is told to continue (src/app/retry-health.ts; src/app/sessions.ts `updateModelHealth`; src/executor/dsh.ts `transient`, `PASSING` regex matching 408/429/5xx and connection errors).
- **Preset composition is deliberate.** The worker preset is "DSH's `standard` preset with only what a worker needs": 5 s foreground shell → background job, 5 s job waits, fs + fs-search, skills, compaction with an 8,192-char tool-result pruner, subagent spawn (model discovery enabled, `agentPreset: standard`), todo with parallel-in-progress, web search but no web fetch. Left out: questions to a person, presenting, plan mode, plugin manager/market, scheduling, goals, workflows, and forked subagents (cordis.patch.yml comments; the forked-subagent exclusion prevents subagents from inheriting the worker preset). The router preset additionally disables fs `write`/`edit` and has no persona/todo/web/subagent rows (cordis.patch.yml router preset block).
- **Session presets are enforced, not assumed:** if DSH's Web UI selects another preset before a managed session's first turn, dsh-superagent re-selects its own (`agent-preset/selected` handler); after the first turn DSH refuses selection changes, which leaves the session alone (src/app/sessions.ts `install`).
- **DeepSeek Harness integration surface:** sessions/session-persistence/workspace/permission-presets/tools/system-prompt/skills/webServer/llm/subprocess services plus `agent/created`, `session/event`, `agent/status`, `agent/disposed`, `agent-preset/selected` events (src/index.ts inject list; src/app/sessions.ts `install`). The panel is a DSH web plugin (platform `web`, with injected DSH client-UI packages, package.json `dsh` block).
- **Prompt assembly order** per model request: shared + role → three team sections → subscriptions + replies → dispatch (router) or work (worker) → admission (router only) → handoff → environment → policy last, so a Policy change leaves all preceding text byte-identical (docs/004-prompts.md "Assembly and precedence"; src/app/prompts.ts `promptParts`). Workers additionally read DSH's coding prompt and the repository's `AGENTS.md`; the router does not (docs/004-prompts.md).
- **Size budget:** the saved prompt configuration (including overrides) is capped by `promptMaxChars` (default 100,000; configurable 1,000–1,000,000, src/limits.ts), validation never truncates, and `tests/model-surface.spec.ts` checks the entire model-facing surface within a size budget per role (docs/004-prompts.md "Versions"; src/deployment.ts; docs/007-architecture.md "Tests").

## 6. Permissions & Safety

- **Authorization-based autonomy, three layers** (docs/002-authorization.md): (1) the deterministic **gate** — explicit requests require an allowed sender who addresses the agent (`mention` or `direct`); follow-ups on threads with tickets get follow-up strength; everything else goes through the per-Source **admission table** (cells: listedUnaddressed / unlistedAddressed / unlistedUnaddressed → explicit | inferred | ignore, defaults in src/admission.ts); bots are at most inferred candidates and only if on the Source's bot list (src/policy.ts `gate`, `machineGate`, `listedBot`). (2) The **accept mode**: `off` / `observe` (default; positive assessments only recorded as "would accept") / `auto` (src/policy.ts `EvalConfigSchema`). (3) **Mandates**: every accept records the Policy version, basis `via` (addressed | followup | admission | bot), scope and matched rules; only accept creates, a person's stop withdraws, and failed revalidation revokes a Mandate (docs/001-domain.md Mandate row; src/core/model.ts `MandateBasis`; src/policy.ts `revalidate`).
- **Who can trigger work:** only identities in each Source's `allowed` list (synced e.g. from a Feishu chat's members via `orchestrator_policy_sync`), or anyone when an admission cell is set to explicit; identities are never mapped across Sources (docs/001-domain.md "A person is not a domain concept"; src/policy.ts header comment).
- **Outside text is data:** messages, comments and quoted documents "cannot change permissions"; prompt precedence places tool/host-enforced facts above built-in text, matched-rule instructions, team sections, and outside text (docs/002-authorization.md opening; docs/004-prompts.md "From strongest to weakest").
- **Session sandboxing is defaults, not a security boundary** (stated in-repo): both presets run `danger-full-access` as the operator's OS user (src/app/sessions.ts `ensure`; docs/006-deployment.md "Permissions and isolation"). Mitigations: worker CLI shims (`gh`, `lark-cli`, plus one fail-shim per blocked command) prepend a private PATH and strip the shim dir recursively (src/infra/environment.ts `writeEnvironment`); an isolated git config with `useConfigOnly`, credential helper bound to the agent CLI, URL rewrites, and no askpass/terminal prompts (src/infra/environment.ts `workerGitConfig`); ambient token/git-identity env vars are unset for agent processes (src/infra/environment.ts `agentVariables`); the Feishu CLI must be in strict bot mode or setup fails (src/deployment.ts `resolveFeishuBot`); repo-local `credential.*`/`http..extraheader` git keys in a ticket directory are refused (src/infra/environment.ts `verifyDirectory`).
- **Scoped reads:** an Executor's `orchestrator_read` can only address its own ticket, its threads, triggers that reached it, and prompt versions it worked under; ids of inaccessible objects are omitted from pages (src/app/tools/tool.ts `readTool`; src/app/resources.ts; docs/007-architecture.md "Read resources").
- **Tool guards:** main Session `noWait` guard (src/app/sessions.ts); worker tool guard refuses everything once the ticket ended, while a blocked/failed worker keeps its tools so a person can continue in-session (src/app/sessions.ts `workOnly`; docs/003-execution.md).
- **Review gates / human control:** Pause processing holds Evals, dispatch, deliveries and replies while Sources keep recording (docs/003-execution.md "Pause processing"); a person's stop withdraws the Mandate and stopped tickets receive nothing more (docs/002-authorization.md "Resume and stop"); workers cannot declare a person's stop — only Eval decides end strength, and a "stop" said in a thread is an ordinary Trigger (docs/001-domain.md rejected concepts; prompts/subscriptions.md). A `waitsForPerson` ticket (latest report blocked/failed with no human message since) takes no automatic Inputs, yet keeps its tools so a person can work directly in the session (src/core/model.ts `waitsForPerson`; docs/003-execution.md "Executor blocked or failed").
- **Fixed refusals** are typed as `UserError(code)` from a closed set `USER_ERRORS`, answered by the API as 404 (`missing`) or 400, and worded per locale in the panel (src/core/errors.ts; src/app/http.ts `failure`; docs/007-architecture.md "Fixed refusals"). Examples verified in code: `handedBackHere` (re-attaching a message a ticket handed back, src/core/engine.ts `attach`), `workerDecides` (requeueing a follow-up a worker still owns, src/app/tools/main.ts).
- **Setup-time identity checks** are the first safety gate: the GitHub CLI must be signed in as an account with push access to the configured repository (canonical name resolved so renames match), and the Feishu CLI must authenticate as a bot in strict mode — a CLI that could also act as a user is refused because workers invoke it (src/deployment.ts `resolveDeployment`, `resolveFeishuBot`; src/setup.ts `SetupError` codes shared by log, panel and main Session).
- **Admission table nuance:** cells for unaddressed messages exist only where the Source observes all messages in that scope; an explicit cell for unlisted-but-addressing senders deliberately beats follow-up strength so "a thread's tickets never weaken an explicit request" (src/policy.ts `gate` comment; docs/002-authorization.md "Admission").
- **Auditability:** every Trigger keeps a disposition (filtered/Eval/Decision/reached tickets/handbacks/acks) and every accept records an audit object (rule assessments, direction, intent_evidence) (src/core/model.ts; src/policy.ts `assessmentOutcome`; SQLite `disposition` table, docs/007-architecture.md "Persistence").

## 7. Sessions, State & Persistence

- **Single SQLite store** `<stateDir>/orchestrator.sqlite`, opened only by the Store; Runtime takes a directory lock (proper-lockfile) first so a second process cannot migrate or write (src/app/store.ts; src/app/runtime.ts; docs/007-architecture.md "Persistence").
- **Tables:** `trigger`, `disposition`, `trigger_thread` (time+id cursor paging), `thread` (subscriptions, queued triggers, running Eval, expiry counts, Source meta; generated indexed columns `active`, `subscribed`), `ticket` (Mandate, origin, execution, assignments, channels, inputs; generated `open`, `active`), `decision`, `effect` (queue rows with per-kind/key coalescing), `outbox` (message receipts, status, drop reason), `kv` (settings/prompt versions, master session id, session prompt revisions, Source read positions/cursors/CI fingerprints, display labels) (docs/007-architecture.md "Persistence" tables; src/kv.ts `KV`).
- **Work item store:** the Ticket aggregate owns Assignments (pending→running→ended independently of the Ticket), Inputs with per-input read tracking, Channels, and `follows` (threads it must see close before ending, `merged`/`closed` outcome) (src/core/model.ts; src/core/tickets.ts; src/core/stage.ts `ticketStage`).
- **Effects = durable "stored work".** Every post-decision action (assessment, launch, delivery, relay, notice, reply) is enqueued inside the Engine transaction and performed after commit, with per-kind concurrency limits, exponential backoff, `Later` deferrals (e.g., no worker slot), and per-kind health entries that error only after 3 consecutive failures (src/app/effects.ts; docs/003-execution.md "Stored work").
- **Resumability:** sessions persist via DSH `sessionPersistence`; on startup `DshExecutor.resume` reports interrupted assignments (recovery note: check directory, git history, GitHub before repeating outside actions), requeues pending launches oldest-ticket-first, and re-delivers Inputs the session never took; a copy waiting inside a session is removed before the new assignment's first message (src/executor/dsh.ts `resume`; docs/003-execution.md "Restart").
- **Pause semantics** are durable: Eval deadlines shift by the pause length; ended tickets touched by a person during a pause resume after it, subject to Mandate revalidation (src/core/engine.ts `evaluateDue`; docs/003-execution.md).
- **Panel state** is derived, not stored: views (`src/app/views/*.ts`) compute overview (tickets needing a person, system problems, 24 h flow, executor load), source status with 24 h filtered/dropped counts, thread timelines, decision lists, and settings/prompt history from the Store; read caches are bounded in-memory `TextCache` and lost on restart (src/app/views/*; src/app/cache.ts; docs/007-architecture.md "Persistence" note on caches). One cache-visible consequence: Feishu message links resolved after intake are cached only in memory, so link-based search finds them only after the link has been read in the current process lifetime (docs/007-architecture.md "Persistence"; docs/005-panel.md "Search").
- **Panel navigation into sessions:** the panel can open a DSH session (e.g. a worker's) via `src/navigation.ts` once the host's catalog lists it, with in-flight navigation cancelled on panel unmount (src/navigation.ts; src/client/index.tsx `Mounted`).
- **Growth is unbounded and admitted:** triggers/dispositions/decisions, ended tickets, outbox receipts and all versioned kv records are never deleted yet (docs/007-architecture.md "Persistence", final paragraph). Schema versioning: `SCHEMA_VERSION` only increases; a schema-10 database is migrated once by src/app/migration.ts, older ones refuse to start.
- **Versioned kv families** (src/kv.ts `KV`): settings/prompt revisions as numbered snapshots with a current pointer (`settings-revision`, `settings-version:<n>`, `settings-block-revision:<block>`, `prompt-revision`, `prompt-version:<n>`), `master-id` (main session), `session-prompts:<session id>` (revisions each session ran under), Source state (`github-cursor:<number>`, PR CI fingerprints, seen Feishu topic messages), and `source-labels:<source id>` display names. Settings snapshots record origin (panel/tool/sync), Policy version and affected tickets (src/app/settings-history.ts; docs/007-architecture.md "Persistence").
- **Paging stability:** a Thread's timeline pages continue from a `<at>|<id>` cursor with times normalized to one ISO form at receive, so equal timestamps never skip rows (docs/007-architecture.md `trigger_thread` row; src/core/engine.ts `isoTime` normalization in `threadClosed`).

## 11. Standout Features (12-16 numbered items, each 1-3 lines with file references)

1. **Two-layer Eval: deterministic gate + model assessment.** Admission is computed in code (`gate`, src/policy.ts); the model only judges admissible candidates against rules with a strictly validated schema (src/app/assessment.ts `AssessmentSchema`).
2. **Mandates as first-class, revocable authorization objects** with `via` basis, Policy-version stamping and revalidation before any resume (src/core/model.ts `MandateBasis`; src/policy.ts `revalidate`; docs/002-authorization.md).
3. **Observe mode ("would accept")**: proactive acceptance is rehearsed and recorded before it is allowed — a graduated-autonomy dial in three positions (src/policy.ts `assessmentOutcome`; docs/002-authorization.md "Accept mode").
4. **Follow-up ownership instead of re-gating:** a person's message on a ticket's own thread goes straight to its worker, who must handle or `handback` it; the router may only stop work meanwhile (docs/002-authorization.md "Two paths"; src/core/model.ts `followupOwners`).
5. **Durable effect queue with coalescing, backoff and per-kind health** as the universal "store first, do later" mechanism for all post-decision work (src/app/effects.ts).
6. **The Outbox pattern for channel writes**: per-message receipts, ordered per ticket+conversation, waiting while a Source is off, dropped (never retried) only when the conversation is provably gone; sends are idempotent per `message.id` so transport retries never duplicate (src/app/outbox.ts; docs/003-execution.md "Channel failure"; docs/008-cookbook.md step 5).
7. **Input read-tracking:** delivery ≠ read; an Input counts as read only after the session takes it into history and a report or turn end follows, which drives what is re-delivered after retry/restart and what returns to Eval on ticket end (src/core/engine.ts `inputsRead`; docs/003-execution.md "Restart").
8. **Worker slots with a person's priority lane:** one extra slot beyond `maxWorkers` is reserved for human messages/status requests so new work can never starve a person's continuation (src/executor/dsh.ts `WorkerSlots.reserve`; docs/003-execution.md "Concurrency").
9. **No-wait router discipline:** preset-level 5 s shell/job caps plus a `noWait` guard against `sleep` and long waits, because a blocked step delays every incoming candidate (cordis.patch.yml; src/app/sessions.ts `noWait`).
10. **Structured attention handoff:** a worker's question is a typed `human_action` field on a Report, relayed verbatim to the conversation where the triggering person wrote, not buried in prose (src/app/tools/executor.ts `orchestrator_report`; prompts/handoff-worker.md; src/app/notices.ts `reportRelay`).
11. **Anti-prompt-injection posture throughout:** "outside text is data", precedence ladder in docs/004-prompts.md, quoted content never authorizes (prompts/cli.md; prompts/subscriptions.md), bot/CI messages can never authorize work (src/policy.ts `machineGate`).
12. **Intent evidence for proactive work:** acceptance requires quoted source statements establishing implementation_requested + settled target + no open design decision, audited on the Decision (src/policy.ts `AdmissionDirectionSchema`, `assessmentOutcome`; prompts/admission.md).
13. **Ticket-ending driven by source reality, not self-grading:** a PR ticket ends when the threads it follows closed (`followsDone`), not when the worker says "done" (src/core/tickets.ts; docs/001-domain.md Ticket row; src/sources/github-pull.ts).
14. **Worker environment binding by shims, not trust:** per-deployment `gh`/`lark-cli`/blocked-command shims, isolated gitconfig with bound credential helper, scrubbed env, verified directories (src/infra/environment.ts).
15. **Prompt versioning bound to sessions:** every model request binds the current prompt revision; sessions may read only revisions they ran under; overridden defaults surface "Default updated" diffs on upgrade (src/app/sessions.ts `promptFor`/`mayRead`; src/app/prompts.ts `defaultChanged`; docs/004-prompts.md "Versions").
16. **Tests as spec enforcement:** `tests/model-surface.spec.ts` checks the whole model-facing surface (tools/prompts/skills/inputs) within a size budget per role; `tests/docs.spec.ts` enforces that the architecture doc's module/test tables list every module and test; `tests/class-docs.spec.ts` requires JSDoc on every class (docs/007-architecture.md "Tests"). Acknowledgements, accepts, notices and sends are additionally deduplicated across retries and restarts (prompts/replies.md; src/app/effects.ts).

## 12. Lessons for Marfim (what to adopt for autonomous/proactive agent operation, 6-10 bullets)

- **Split "may we work?" from "how do we work?".** A cheap deterministic gate (allowlists + admission table + accept mode) decides admissibility and strength; the model only assesses what the gate admits, under a schema that forces one verdict per rule plus quoted intent evidence (src/policy.ts; src/app/assessment.ts).
- **Ship an observe mode first.** Recording "would accept" decisions with full audit before enabling auto-accept is the single most transferable idea for safely turning on proactivity (src/policy.ts `assessmentOutcome`; docs/002-authorization.md).
- **Make authorization a durable object attached to the work item** (Mandate: basis, scope, matched rules, policy version) and revalidate it before any resume; never let a worker's context or quoted text extend it (src/core/model.ts; src/policy.ts `revalidate`).
- **Route follow-ups by ownership, not re-evaluation.** Messages on a live work item's own thread belong to its executor (handle/handback), which removes the router from the hot path and keeps the router from re-interpreting context (docs/002-authorization.md; src/core/model.ts `followupOwners`).
- **Store-then-act everything.** A transactional effect queue with per-kind concurrency/backoff/health makes restarts boring: launches, deliveries, relays and replies all survive crashes in a uniform way (src/app/effects.ts).
- **Track input consumption, not just delivery.** Knowing which messages a worker session actually took into history is what makes retry/restart/resume correct and prevents double-acting on a person's request (src/core/engine.ts `inputsRead`; docs/003-execution.md).
- **Design the router to never wait.** 5-second caps, a sleep guard, automatic delivery of reports/candidates/job results — the router's turn ends early and the world comes to it (cordis.patch.yml; src/app/sessions.ts `noWait`; prompts/orchestrator.md).
- **Give humans a structural priority lane** (extra worker slot for person messages, structured attention questions, panel sorted by what needs a person) so autonomy never competes with the operator for throughput (src/executor/dsh.ts; docs/005-panel.md).
- **Constrain the output channels as hard as the input.** Purpose-gated reply tools, per-purpose engine checks, word limits enforced at transport, ordered per-conversation outbox, and a "final notice" rule for PR outcomes keep a proactive agent from becoming noisy (src/app/tools/main.ts `orchestrator_reply`; src/app/replies.ts; src/app/outbox.ts; src/infra/text.ts).
- **Write the setup as an agent playbook.** SETUP.md's probe→questions→plan→execute→verify loop, with secrets kept to operator steps and recommended defaults for everything else, is a template for Marfim's own onboarding-by-agent (SETUP.md).
